# CI/CD — one pipeline, one caller per agent

Pipeline: [.github/workflows/agent-deploy.reusable.yml](../../.github/workflows/agent-deploy.reusable.yml).
Callers: `.github/workflows/<agent>.yml`, one per agent, generated by
[/new-agent](../../.claude/skills/new-agent/SKILL.md).

The split exists so a pipeline fix reaches every agent at once, and adding an agent is a caller
file rather than a new pipeline to keep in sync. Callers say only **which** agent and **when**.

## Convention over configuration

A caller passes one input, `agent: <name>`. Everything else is derived:

| Derived | From |
|---|---|
| Image | `ghcr.io/${{ github.repository_owner }}/<name>` |
| Build context + Dockerfile | `agents/<name>/` |
| VM directory | `/app/<name>` |
| Compose file | `agents/<name>/deploy/docker-compose.yaml` |
| Config shipped | `agents/<name>/agent_config.yaml` |

Each is overridable, which is what makes a second stack for the same agent possible — a prod variant
is the same image with a different `deploy_dir` and `config_file`, no code fork. Promotion to such a
stack uses `build: false` with an explicit `image_tag` from a `workflow_dispatch`, so putting an
agent somewhere consequential is always a deliberate act, never a side effect of merging.

## Design choices and the failure each prevents

- **Deploy the exact image the build produced.** `IMAGE_TAG` comes from `metadata-action`'s `version`
  output rather than being re-derived in bash — one source of truth, no tag-parsing step to get wrong.
- **`type=sha` on every build.** Without an immutable tag, a merge publishes only the mutable
  `latest`, and the deploy's closing `docker image prune -f` reaps the previous image as soon as
  `up -d` releases it. `bb-trade-agent` hit exactly this: a promotion deleted its own predecessor
  and rollback became "rebuild from the old commit". The sha tag is the rollback handle.
- **Secrets stay on the VM.** CI ships only the image, the compose file, and the secret-free config.
  It never reads or writes `.env.<agent>`, the database, or any session file.
- **Ephemeral registry auth.** The VM logs in to GHCR with the per-run `GITHUB_TOKEN`, piped over SSH
  **stdin** so it never appears in argv or logs, and `docker logout` runs at the end. Nothing
  long-lived is stored on the VM.
- **Host keys are scanned per run, not pinned.** CI runs `ssh-keyscan` into the runner's
  `known_hosts` and keeps `StrictHostKeyChecking=yes`, so a key that changes *during* a deploy aborts
  it. It does **not** protect against a MITM at scan time — whatever answers the scan is trusted.
  This is a deliberate downgrade from a committed `known_hosts`, taken because the pinned file went
  stale. To restore real pinning: verify the VM's fingerprint out of band, commit
  `ssh-keyscan 157.90.18.149 > deploy/known_hosts`, and install that file in the workflow
  instead of scanning.
- **A constant `vm-deploy` concurrency group on the deploy job.** Two agents whose path filters both
  match a push would otherwise deploy at the same time and share root's `~/.docker/config.json`,
  where one run's `docker logout` breaks the other's in-flight `pull`. The group serializes only the
  deploy job, so builds still run in parallel. The caller's own workflow-level concurrency guards
  only itself and is not enough.
- **A post-deploy running check.** Before it existed, a stack that pulled a broken image and
  crash-looped reported a green deploy. The step waits, then fails with `docker compose ps` and the
  last 50 log lines attached.
- **`persist-credentials: false` on every checkout**, and every third-party action pinned to a
  full commit SHA — a mutable tag on an action is an unreviewed code path with repository access.

## What CI does not do

It does not create the VM's secrets file. `/app/<name>/.env.<name>` is operator-provisioned once,
before the first deploy — see [runbooks/new-agent-vm-setup.md](../runbooks/new-agent-vm-setup.md).
A deploy against a missing env file fails at `docker compose up`, which is the intended behaviour.

## Repository secret

`SSH_PRIVATE_KEY` — the deploy identity for `root@157.90.18.149`. It must be a repository
**secret** (encrypted), never an Actions *variable*. It is a different key from the one Claude uses
over SSH MCP ([ssh-mcp.md](ssh-mcp.md)), so revoking one does not disturb the other.

## Gaps

- **No host-key pinning** (see above) — the one place this pipeline is weaker than the setup it was
  derived from.
- **No rollback runbook.** `type=sha` gives every build an immutable handle, so redeploying an older
  revision is possible (`build: false` with that tag) — but the procedure has not been exercised.
